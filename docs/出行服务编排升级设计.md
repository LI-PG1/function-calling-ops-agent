# 出行服务编排升级设计｜从设备运维到出行服务编排 Agent

> **文档性质**：系统设计（介于设计方案与模块设计之间）｜**v0.1**｜2026-07-29
> **问题设定**：出行服务编排（双模式；场景分类参照天池公开赛题的 8 类标准场景，https://tianchi.aliyun.com/competition/entrance/532505）
> **升级总纲**：**类型锁定不变，题材层切换**——从「设备运维」升级为「出行服务编排」（车主自驾 + Robotaxi 双模式）；工程层（可靠性七件套 / 编排循环 / 工具框架 / 评测设计 / 模型接入）复用约 70–80%，素材层按赛题能力体系重做。
> **配套文档**：`设计方案.md`（系统级）、`模型选型.md`

---

## 1. 为什么升级：四个理由

1. **场景体系完备**：8 类标准场景、双模式工具清单、五维能力要求——覆盖了出行服务的主要需求类型，可直接作为场景设计的需求来源。
2. **能力维度匹配**：核心能力为"多工具编排 + 安全边界 + 服务闭环"，与本项目的技术路线（多工具 Function Calling + 长链路 + 可靠性工程 + 评测）逐条对应。
3. **场景承载充分**：智能出行是 2026 年的热点方向；双模式（车主 / Robotaxi）让工具动态装载、身份识别等工程点有真实承载。
4. **差异化落点明确**：多数同类实现止于演示，**失败注入、可靠性压测、评测闭环、迭代记录**恰是可拉开差距之处，也是本项目的投入重点。

**定位口径（三条）**：

1. **场景自建**：场景虚构、素材自建；需求分类参照公开场景体系与需求维度，实现层不含任何外部作品的代码或方案；
2. **工程独立**：架构、工具、护栏、评测链路均为自行设计实现；
3. **可持续扩展**：场景与工具按配置驱动，新增场景只需补规则与工具 spec。

## 3. 能力项 → 设计落点（五项能力拆解）

### 3.1 场景理解 → 场景路由升级

**现状**：规则版 fast/agent 二分类。**升级为三层路由**：

```
用户请求 → ① 规则快路径（高危关键词/行驶态硬规则，毫秒级拦截）
        → ② LLM 场景标签（8 类场景 + 身份：车主 / Robotaxi 乘客 + 风险等级）
        → ③ 宽表兜底（无法归类 → chat 轻量应答）
```

- 场景标签集：`tired`（疲劳）/ `child`（亲子）/ `longtrip`（长途补能）/ `commute`（通勤）/ `robotaxi_lost`（找不到车）/ `pickup_abnormal`（上车点异常）/ `dest_change`（改目的地）/ `passenger_help`（乘客不适求助）；
- 路由输出决定**工具集动态装载**（车主模式 8 个 / Robotaxi 模式 +4 个）——"避免一个万能 Prompt 包打所有工具"（社区共识打法）；
- 场景理解的核心考题是"**读懂没说出口的那句话**"：如"我有点困"→ 疲劳风险（≠播放音乐）——路由提示词与安全规则库共同承接，进评测集。

### 3.2 服务编排 → 工具清单（12 + 1）

| # | 工具 | 模式 | 说明 |
|---|---|---|---|
| 1 | `get_vehicle_status()` | 共用 | 车辆状态（位置/电量/行驶态/行程） |
| 2 | `assess_risk(situation)` | 共用 | 风险评估（规则库 + LLM）→ 风险等级与策略 |
| 3 | `search_safety_rules(query)` | 共用 | 安全规则库检索（Embedding） |
| 4 | `control_climate(action, zone?)` | 车主 | 空调（制冷/制热/风量/除雾） |
| 5 | `control_seat(action, zone)` | 车主 | 座椅（通风/加热/按摩/放倒） |
| 6 | `navigate(destination)` | 车主 | 导航设置 |
| 7 | `find_parking(near?)` | 车主 | 停车场查询 |
| 8 | `find_charging(near?)` | 车主 | 充电站查询 |
| 9 | `play_media(category)` | 车主 | 提神媒体（疲劳场景配合提醒，不单独作为处置） |
| 10 | `query_ride_order(order_id?)` | Robotaxi | 订单查询 |
| 11 | `modify_pickup_point(order_id, point)` | Robotaxi | 修改上车点 |
| 12 | `change_destination(order_id, destination)` | Robotaxi | 修改目的地 |
| 13 | `escalate_human(reason, priority)` | 共用 | 转人工客服 |

**三段式调用范式**（社区共性，采纳）：先建上下文（`get_vehicle_status`）→ 风险评估（`assess_risk`）→ 服务执行（车控/导航/订单）——与可靠性设计天然衔接（每段都可能失败并触发重试）。

**编排纪律**：计划-执行循环保留；并行调用用于"无依赖组合"（如同时查停车场 + 充电站）；`max_iter` 与降级保留。

### 3.3 安全边界 → 双层护栏 + 声明式规则库（本升级的工程核心）

**L1 提示词层**：系统提示注入场景策略；每次工具调用带 reason（可解释）。

**L2 代码硬规则层**（"模型失误仍有代码兜底"——公认亮点，必须落进代码）：

- `pre_check`：危险动作前置拦截——行驶态下的开门/解安全带类指令、超速设定、儿童独留车内的温控关闭、无订单状态下修改上车点；
- `post_review`：输出后校验——命中高风险场景时，输出**必须**包含安全提示与禁止动作列表，否则打回重写。

**声明式安全规则库** `config/safety_rules.yaml`：

```yaml
- id: fatigue_highway
  scene: [tired]
  risk: high
  strategy: [remind, navigate_to_rest_area]   # 提醒 + 导航至服务区，拒绝"仅播放音乐"式敷衍
  must_output: [safety_tip]
- id: moving_child_unattended
  scene: [child]
  risk: critical
  strategy: [refuse, escalate]
  must_output: [refusal_reason, safety_tip]
```

策略词表：`allow / remind / refuse / degrade / escalate`——规则可版本化、可评测（"规则迭代"成为 CHANGELOG 的一类条目）。

**转人工兜底（HumanAgent）**：`escalate_human` 触发条件——critical 风险、连续失败降级、用户显式要求；人工工单 mock 服务承接。

### 3.4 结果输出 → 输出协议四件套

```
① 自然语言回复（对用户）
② 结构化服务计划（工具调用序列 + 每步 reason）
③ 禁止动作列表（命中的安全规则）
④ 安全提示（高风险场景必有）
```

四件套全部进 state 与 trace——可解释性既是评分胜负手，也是"调用留痕"工程点的自然延伸。

### 3.5 可体验呈现 → Demo 升级

- Streamlit 车机 HUD 风格深色界面：左侧对话、右侧服务计划与工具 trace 实时可视化、风险标识灯；
- 场景快选按钮（8 类场景一键载入示例请求），30 秒内可完成一次完整体验；
- 公网部署（Hugging Face Spaces 或同类免费托管）为可选增强项；演示界面本地运行（`.venv/Scripts/streamlit run app.py`），部署配置已备齐。

## 4. 多 Agent 分工（叙事合并）

"多 Agent 协作"的落点——同图谱、异角色：

| 角色 | 职责 | 对应实现 |
|---|---|---|
| Router Agent | 身份/场景/风险标签 → 工具集动态装载 | `router.py` 升级 |
| Planner / Executor | 计划-执行循环 | `agent/loop.py` 扩展 |
| Safety Agent | 规则检索 + 风险评估 + 护栏审查 | 新增（可挂 Critic 提示词 + 规则库） |
| Critic | 结果自检（独立模型，选型已定案） | 选型档 API |
| Human Agent | 转人工兜底 | `escalate_human` + 客服 mock |

**多智能体界定**：角色分工由提示词与节点实现承载，Planner / Router / Executor 在同一进程内运行；独立模型实体仅 Critic（异构档）。

## 6. 评测设计（重设计 + 安全专项）

### 6.1 指标集

| 类 | 指标 | 口径 |
|---|---|---|
| 功能 | 多步任务完成率 | 对照"无规划基线" |
| 功能 | 工具选择/参数准确率 | 序列 + schema 校验比对 |
| 路由 | 场景识别准确率 / 分流延迟 | 8 类标签 + 快路径占比 |
| **安全（新增核心）** | **危险请求拦截率** | 危险子集：pre_check + post_review 双层拦截，目标 100% |
| 安全 | 输出合规率 | 高风险场景输出含四件套的比例 |
| 可靠性 | 失败注入下完成率 / 重试成功率 / 压测 P50/P95 / 超时率 / max_iter 触顶率 | 沿用 |
| 失败模式分布 | 误选/参数错/超时/规划错/护栏误拦（新桶）/降级触发 | 分桶统计 |
| 外测 | BFCL / API-Bank 对照 | 沿用（函数调用准确率口径） |

**新增分桶"护栏误拦"**：L2 硬规则的误伤同样需要量化——安全与可用性的平衡属于必须给出数字的工程问题。

### 6.2 迭代闭环扩展

失败分类新增两类：`rule_miss`（规则库缺条）→ 补规则进 YAML；`rule_false_positive`（误拦）→ 调规则阈值/条件——**规则版本化写入 CHANGELOG**，与技能迭代同轨。

### 6.3 安全对照实验（差异化叙事的核心证据）

| 对照 | 说明 |
|---|---|
| 无护栏 vs 双层护栏 | 同危险请求子集：拦截率对比——量化 L2 代码规则的价值 |
| 规则库 v1 vs v2 | 一轮规则迭代前后的误拦率/漏拦率对比 |

## 8. 模型选型适配（结论：五角色不变，三条适配）

| 适配 | 内容 |
|---|---|
| ① 主 FC 裁决权重微调 | 工具域从"运维 API"变为"车控/订单 API"——业务语义更生活化，35B-A3B 的通用工具数据优势上升；**裁决规则不变**（实测差异 ≤2 条取零成本者），但冒烟增加一轮"生活化参数填充"测试（如"有点困" → 场景判断） |

**成本结论不变**：全周期 ¥60–110 量级；若主 FC 裁决选 35B-A3B（已在手）降至 ¥10–30。

## 9. 验收增量（在设计方案 §7 基础上新增）

1. 工具清单 ≥12 个且按模式动态装载；场景路由三层落地（含高危快路径）；
2. 双层护栏进代码：危险请求子集拦截率实测（目标 100%）+ 误拦率实测（分桶可见）；

4. 任务集按 8 场景重建（≥35 条）+ 失败注入矩阵全覆盖；
5. 安全对照实验有数字（无护栏 vs 有护栏）；
6. Demo 为车机 HUD 风格且含 8 场景快选；公网部署为可选增强项；
7. 迭代记录 ≥1 轮（技能或规则两类均可），CHANGELOG 前后指标可证。
