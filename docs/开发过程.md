## 2. 关键节点与实测数据

### 2.1 规则引擎从"关键词"到"双条件"

初版规则只看动作参数（如 `action == unlock`），实测发现行驶中与驻车状态下的同一动作风险完全不同。
改为 `arg_checks` + `state_checks` 双条件后，才具备「文本无害但状态危险」的识别能力——
这也正是隐性诱导用例能被拦下的原因。

### 2.2 任务集四轮迭代

| 轮次 | 变更 | 完成率 |
|---|---|---|
| r1 | 首版任务集（38 条） | 37.0% |
| r2 | 修复计划提示词缺 `{task}` 注入、空计划处理缺陷 | 85.2% |
| r3 | 补场景覆盖至 38 条全绿 | 100% |
| r4 | 任务集扩至 43 条（补 5 条隐性变体） | 43 条全绿 |

r1 的两处缺陷属于实现 bug 而非模型能力问题：计划提示词没有把任务文本注入，计划器全程看不到请求内容；
空计划未做处理导致后续节点拿不到步骤。这类问题只有靠端到端任务集才暴露，单测覆盖不到。

### 2.3 多轮基准的三次决策

第一次跑完 500 条得 24.0%。随后做了两组对照：

1. **加纪律提示词**：两版都导致退化（base 38% → 18%），回滚。结论是通用 system prompt 反而更稳；
2. **步数上限**：8 → 24，子集 50×5 上 +4，全量复跑验证 +6（120 → 126/500）。

期间发现同一配置两次运行不能逐题复现（约 ±12% 方差），因此确定「A/B 必须 ≥50 题样本 + 至少两次复跑」
的口径，避免拿单次小样本波动当归因依据。

### 2.4 失败处置口径的由来

失败注入演示里，模型对「重试后仍失败」的回复是「我这边重试一下～您稍等」——实际已无重试步骤。
这是空承诺。修正方式是在合成提示词里加一条硬约束：必须说明哪项失败并给出可行动替代，
不得声称无步骤支撑的后续动作。改完后单例复测与 43 条全量回归均通过。

## 3. 工程纪律

- **异常不静默**：可靠性层捕获异常后转换为「非结果」交回上层，由上层决定重试或降级，不做 `except: pass`；
- **配置外置**：场景、规则、提示词全部在 `config/`，改规则不碰代码，便于对照实验成立；
- **每轮留痕**：每次迭代记录变更清单与前后指标，报告归档在 `eval/archive/`；
- **判分可信度**：外测接入官方 checker 后，先用 gold 轨迹重放 100/100 校准，确认判分无系统性偏差，
  再解释模型得分。
