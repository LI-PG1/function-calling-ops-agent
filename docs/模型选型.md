## 1. 需求推导：链路对模型的约束

### 1.1 调用点清单（模型 → 链路映射）

链路（设计方案 §2）：入口分流 → 快路径直答 / Agent 循环（Plan → 工具调用 → 合并观察 → 判续 → Critic → 输出）。

| # | 调用点 | 角色 | 频率 |
|---|---|---|---|
| 1 | `route` 分流判定（fast / agent） | 轻量档 | 每请求 1 次 |
| 2 | 快路径直答（手册检索 → 回答） | 轻量档 | fast 路径每问 1 次 |
| 3 | Plan：整体计划生成（M2） | 主 FC | 每任务 1 次 |
| 4 | 循环决策：工具选择 / 参数填充 / 判继续（核心） | 主 FC | 每任务多轮（≤8） |
| 5 | 失败恢复：错误回填后调整重试 / 降级决策 | 主 FC | 失败注入场景 |
| 6 | `Critic` 自检（计划 / 结果校验） | Critic | 每任务 1–2 次 |
| 7 | `search_manual` 检索 | Embedding | 按需 |
| 8 | 评测：结果要点评判 / 失败归因辅助 | Judge | 评测批量（工具序列 / 参数比对为程序化，不耗模型） |

### 1.2 主 FC 模型：六项要求

| # | 要求 | 说明 |
|---|---|---|
| 1 | **FC 协议稳定性** | 严格按 OpenAI tools 协议输出 tool_calls（JSON 可解析、参数符合 schema）；**不夹思考过程** |
| 2 | **多步编排** | 长链路（3–8 步）不迷路：计划一致性、上下文保持、循环终止判断 |
| 3 | **参数填充准确性** | 业务语义 → 参数（如"压缩机 ZX-220 的轴承"→ device_model / part_name） |
| 4 | **失败恢复** | 工具超时 / 500 / 空结果回填后，能调整参数重试或给出降级建议——**本项目第一纪律** |
| 5 | **工程侧** | OpenAI 兼容（现有 `src/llm.py` 按此实现）、temperature=0、批量稳定 |
| 6 | **成本效率** | 每任务多轮调用（高频），激活参数越小越好 |

### 1.3 其余角色

- **轻量档**：分流判定要快（延迟敏感）＋快路径直答要稳（FAQ 式组织检索结果，中文）；
- **Critic**：判断任务（计划合理性 / 结果完整性）——独立于主模型（避免自审盲区），低频；
- **Judge**：结果要点评判——异构于主模型（避免自评偏置），低频；
- **Embedding**：手册知识库检索（3 设备族 / 13 故障 / 16 备件，百条级小库）。

## 2. 市场扫描（Agent / FC 侧，2026-10）

**关键事实**：Function Calling 与 agentic 能力是 2026 年模型竞争的主战场，三个信号：

1. **"工具调用 + 失败恢复"成为专门训练目标**——Qwen3-Coder-Next 以"长程推理、复杂工具调用、执行失败恢复"为核心卖点；新一代模型普遍在 TAU / MCP / Toolathlon 类工具榜单上跑分（本项目的失败注入设计正踩在这个趋势上）。
2. **通用与专用双线并行**——Qwen3.6 系（TAU3-Bench 67.2 / MCP-Atlas 62.8）代表通用 agentic；Coder-Next 代表 agent 专精线。**工具调用能力在不同量级模型间已趋同、在失败恢复与长链稳定性上拉开差距**。
3. **1T 级天花板不可部署**——Kimi K2.6（agentic 最强档）/ DeepSeek V4-Pro 为 1T 级 MoE，部署不现实；本项目按"可部署优先"选型，API 仅用于低频角色（Critic / Judge）。

## 3. 主 FC 模型选型

### 3.1 候选对照表

| 候选 | 架构 / 许可 | 公开证据 | 部署 | 定位 |
|---|---|---|---|---|
| **Qwen3-Coder-Next** | 80B / **3B 激活** · 256K · Apache 2.0 · **原生非思考模式** | 官方定位：长程推理、复杂工具调用、**执行失败恢复**专精；SWE-bench ~73.4–74.2；适配多种 agent 脚手架 | Q4 ~48–52GB（48GB+ 卡或双卡） | **主选** |
| **Qwen3.6-35B-A3B** | 35B / 3B 激活 · 256K · Apache 2.0 | 通用 agentic：TAU3 67.2 / MCP-Atlas 62.8 / Claw-Eval 68.7（新版工具链测评） | Q4 ~22GB 单卡 | **对照（已有·零成本）** |
| Qwen3.6-Coder-32B | 32B · 128K | SQL 专精（与 FC 无关）；FC 能力未验证 | ~24GB | 对照（共享测试位） |
| Qwen3.8-Flash-Next | 125B / 6B 激活 · 新架构（QSA+GDN） | **工具榜最强档**：Toolathlon Verified 73.5 / CoWorkBench 73.9 | 新架构，部署生态待成熟 | **观察（二轮候选）** |
| Hunyuan-80B-A13B-Instruct | 80B / 13B 激活 | BFCL-v3 / τ-Bench / ComplexFuncBench 表现突出（2025 老将） | 已部署 | 兜底 |
| Kimi K2.6 / DeepSeek V4-Pro | 1T 级 MoE | agentic / 工具调用天花板 | **部署不可行** | 排除（API 形态仅用于 Judge / Critic） |

### 3.2 主选论证（为什么是 Qwen3-Coder-Next）

1. **主题逐条对齐**：本项目三根支柱——多步编排（长程推理）、多工具调用（复杂工具调用）、可靠性工程（**执行失败恢复**）——恰是其训练目标；"失败注入"评测设计直接踩在其专精区。
2. **原生非思考模式**：FC 循环对输出格式最敏感（任何思考块都可能污染 tool_calls 解析）——该模型输出天然干净，不依赖 `enable_thinking` 参数控制。
3. **3B 激活**：多轮循环高频调用下推理成本极低（Q4 部署门槛在加载侧，不在运行侧）。
4. **工程适配**：官方适配 Claude Code / Qwen Code / Cline 等多种脚手架 = 工具调用协议经过广泛验证；256K 上下文对多轮消息历史富余。

### 3.3 对照设计与裁决指标

**三档同任务集对照**：Coder-Next（主选）vs **35B-A3B（零成本对照，通用 agentic 数据更贴近业务 API 工具域）** vs Coder-32B（共享测试）。

| 指标 | 口径 |
|---|---|
| 任务完成率 | 期望步骤 / 工具序列比对（程序化） |
| 工具选择准确率 | 选错工具数 / 总调用数 |
| 参数填充准确率 | schema 校验通过率 + 关键参数比对 |
| **失败恢复成功率** | 失败注入子集下：正确调整重试 / 给出降级的比例 |
| 单任务延迟 | 全链路 P50（多轮累计） |

**裁决规则**：完成率与失败恢复率为主指标；若 35B-A3B 与 Coder-Next 差异 ≤2 条（小样本口径），取**零成本者**（35B-A3B 已在手）；Coder-Next 明显占优则部署之。

## 4. 轻量档（分流 ＋ 直答）

| 项 | 方案 |
|---|---|
| 用途 | ① `route` 分流判定（fast / agent，二分类）；② fast 路径直答（检索手册 → 组织回答，中文） |
| 主选 | **Qwen3.5-4B**（新代小档；中文优先；qwen3_5 架构，vLLM 0.19 原生支持） |
| 兜底 | Phi-4-mini-instruct（已可用）；MiniCPM5-1B（极端轻量） |
| 过渡 | 分流判定先沿用**规则版**（`src/router.py` 已实现）——M2 升级 LLM 判定时接入 |

**为什么不复用主 FC 模型**：分流与直答的意义就是绕开 Agent 循环的延迟与成本（快路径指标：直答时延、分流比例）——用小模型是架构逻辑的一部分。

**为什么不在平台现成档里挑**（2026-08-02 复核）：MiniCPM5-1B——分流够快，1B 直答“稳”没把握；Phi-4-mini——中文非强项，且已占兜底位（升主选则降级链断）；30B 级 MoE（Qwen3-30B-A3B / Qwen3.6-35B-A3B）——不满足“小显存常驻”，35B FP8 版 10 tok/s 亦不适合关键路径。

## 5. Critic 与评测 Judge（独立异构档）

**决策点（设计方案 §8）"Critic 用同模型还是独立模型" → 定：独立档。**

| 角色 | 选型 | 理由 |
|---|---|---|
| Critic | **V4-Pro（API）**——与 Judge 同源复用 | 自检模型独立于主 FC（避免"自己检查自己"的同源盲区）；低频（每任务 1–2 次）成本可忽略；若仅部署形态可用 → Hunyuan-80B 兜底 |
| 评测 Judge | **V4-Pro（API）** | 异构于主 FC（Qwen 系）；工具序列 / 参数比对为程序化主指标，Judge 仅评"结果要点"与辅助失败归因 |

**设计取舍记录**：主 FC 与 Critic 分离会引入一个额外的模型依赖——但失败恢复是本项目主题，Critic 的独立性直接强化"可靠性工程"叙事；且 API 低频成本在十元级，值得。

## 6. Embedding（安全规则库检索）

- **主选：Qwen3-Embedding-4B**——与主 FC 共用同一部署环境（一次部署，两条链路共用）；
- **对照：gte-Qwen2-1.5B（平台已部署·零成本）**——与 4B、现役 BGE 同批探针数据裁决（规则：持平取零成本，明显占优再新增部署）；
- 规则库百条级，0.6B 亦可胜任——作为推理资源紧张时的降档；
- 向量库：Milvus Lite / Chroma（设计方案既定），embedding 替换后重建索引（一次性）。

## 附三：API 形态的工程处理

**定性**：主链路自部署 ＋ Critic/Judge API 的混合形态是刻意设计（分配逻辑见附一），不是妥协。API 是否"减分"只取决于一件事——**是否把它当工程面处理**；黑盒式调用才会被追问。

**API 依赖的工程处理（"模型接入层"，接入时实装四件事）**：

| # | 事项 | 现状 | 接入时补 |
|---|---|---|---|
| 1 | 统一接入层 | 已落地：`llm.py`（OpenAI 兼容一次封装，部署 / API 同协议） | provider 配置化（主 FC / 轻量档 / Critic 多端点切换） |
| 2 | 失败处理 | 工具层可靠性七件套已落地；LLM 调用层加固中 | LLM 调用重试退避 ＋ 限流识别 ＋ 超时 |
| 3 | 备选链 | 设计已定（Critic：V4-Pro → Hunyuan-80B 兜底） | fallback 实装 ＋ 切换日志 |
| 4 | 成本可见 | 成本口径已估（§7） | 成本记账（调用量 × 单价 → 每轮评测报告一行） |

**说明口径（一句话）**："主 FC 自部署保证循环高频调用的成本与稳定；Critic/Judge 用 API 换取独立异构与最强判断力——API 依赖通过接入层工程化处理（重试 / 限流 / 备选链 / 成本记账），不是黑盒。"

**API 给不了什么、为什么这里不重要**：不能量化 / 微调 / 看 logprobs、最坏延迟不可控——Critic 与 Judge 为低频角色，这些能力在本场景无需求；数据合规上本项目为合成与公开数据，不涉及数据出境与个人隐私。
